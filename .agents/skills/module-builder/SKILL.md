# Module Builder

## 0. Owner's standing brief (applies to EVERY module — the owner never has to repeat it)

When the owner hands over a tool / HTML / prototype ("another AstroGaami …"), all of this is implied:

1. **Chips and ops only.** Every judgement lives in an op param, a chip or rule JSON; the control lays
   out. A missing capability = a NEW generic op (declared in `op_catalog.py`, one self-check), never
   screen logic or a topic branch in Python.
2. **Deep-research the gaps and fix them.** Read the source end to end, compare with the classical
   doctrine and with the source's own worked examples; a hard-coded tick, a claimed-but-uncomputed
   transit, a typed value the ecosystem already knows, a help text that contradicts the code — each is
   fixed (intent kept, bug named in the rule `_note`). Cite the doctrine (`rule_source` / help).
3. **A case file given = the parity test.** A PDF / screenshot of worked examples is pinned LITERALLY
   in `test_<prefix>_<module>.py` (every number the author wrote), plus a port of the source's own
   algorithm over a sweep. Confirm to the owner which lines match, and name any that differ and why.
4. **Timing tools predict, then score.** A technique that times events lists its predictions from birth
   (windows), each with Register → actual date; accuracy = hit / near (± tolerance) / miss, always
   shown with the chance rate. **Dated life events = the shared store.** A module that reads an event date / age also lets people
   REGISTER events (name, date, area) per chart — `/subject-events/{birth fingerprint}` (per user,
   area ids shared with Chart Proof), delete behind `ConfirmDialog`, one click opens the reading.
   Never a new table for dated events. The list is ONE per (signed-in user, My Charts chart) across
   BCP, Prashna Kosha → Life events & proof and Dasha Transit Event Plus: same `subjectKeyOf`, area ids =
   Chart Proof's, write onto the latest stored list, re-read on `usePageShown()`.
5. **Ship visible.** Guide me script + Tour Video row and render (§9) in the same change — chips/ops,
   Guide me, Tour Video: a module missing any of the three is not done.
6. **Lessons go here.** Every slip found while building becomes a row in §11 + memory, same change.
7. **Reuse first - never reinvent the wheel.** Before building, search for an existing component, control, op or chip.
   Fits fully -> use it. Fits partly -> make it generic so both uses share it. Nothing fits -> only then build.
8. **Professional narration.** Words on screen, in Guide me and in the tour: compact, elegant, professional - with a
   beautiful SVG where a picture helps.
9. **Slow work shows a UEW (owner 2026-10-30, REQ-0055 Try it sat white for minutes).** If ANY step can take more
   than ~1 s - a first page load, a big chart, a backend call, a build, an AI call - the person sees `common/ProgressDialog`
   (or the portal's UEW) AT ONCE with what is happening and the time gone. Anticipate it while building; never wait
   for the owner to find a blank screen.
   GopiHora (2026-10-30) taught two more: (a) the window starts at MOUNT, with the screen's own load (its rule) as
   step one - a window gated on `rule?.x` shows nothing until the rule arrives; (b) the wait times live in a small
   `ui.<screen>_wait` chip bundled as the first-frame value (pattern `ui.vps_console_wait`), never in the screen and
   never in a big rule. A registry control's code still arriving gets the shared window from `common/lazyControl`
   (chip `ui.control_load_wait`). Guards: `agGopiHora.test.tsx`, `common/lazyControl.test.tsx`.
10. **Run your own tests.** A test written but not run is not done. If the machine you build on cannot run it, say so
    as the FIRST line of the report, not the last (REQ-0055: the main test was written, never run, and failed).
11. **Every device, both themes.** Verify AND test on laptop, tablet and phone, light and dark (skill `screen-test`).
12. **Agent + MCP scope** per §8a (free options first), built on the standard frameworks or "no (why)".
13. **Close with status:** what is done, the pending list, what is next.

One module = **ops → chips → rule → control → access → tracking → tour → guards**, in that order.
Nothing skips a layer, nothing reaches past one. `ops-chips-first` is the law this recipe obeys.

Reference module: AstroGaami Tarabalam — op `tara_matrix` (`backend/engine/rule_eval.py`), rule
`backend/engine/data/rules/ag_tarabalam.json`, control
`src/components/runtime/AstrogaamiTarabalamControl.tsx`, workspace screen in
`backend/data/workspaces/astrogaami.json`, guards `backend/tests/test_astrogaami_workspace.py` +
`test_workspaces_complete.py`.

## 1. The layers — what goes where (HARD)

| Layer | Is | Holds | Never holds | Where |
|---|---|---|---|---|
| **Op** | A generic, domain-agnostic computation with params | Arithmetic, astronomy, lookups, list/row algebra; every judgement as a PARAM | A school's constant, a topic name, a threshold baked in | `engine/op_catalog.py` (declare) + `engine/rule_eval.py` (dispatch) |
| **Chip** | ONE named decision: an op expr + default params + `test_cases` | Policy knobs (who may see, which sites, which seats are good), with tests | UI, text layout | `engine/data/chips/<set>.<name>.json` |
| **Rule** | The module's content + configuration | Every constant of the doctrine (scores, tiers, bands, keyword lists, activities, sign tables), the exprs the screen sends, provenance, workspace tag | Python, logic the engine cannot see | `engine/data/rules/<prefix>_<name>.json`, edited in RCB |
| **Control** | The screen. Draws what the server answered | Layout, UI state (tab, date, picked stars, search text), vocabulary labels (code → name) | Scores, thresholds, bands, rankings, sorting by merit, date/dasha math | `src/components/runtime/<Name>Control.tsx`, `Registry.ts` |
| **Python router / service** | Fact gathering + calling chips | Rows, membership, admin flag, files | An `if` on a doctrine or on an institute | `routers/`, `services/` |

Decision test for any line you are about to write: **does it turn data into a judgement?** Yes →
op param or chip or rule JSON. No (layout, formatting, UI state) → the control.

Allowed in a control: choosing between two rule-supplied lists by a SERVER verdict (favourable →
good list), slicing by a rule-supplied max, joining a server row to a label. Not allowed: `if
(score >= 8)`, a sort that ranks, a table of meanings.

## 2. Read the source completely

Every line (page through a big HTML; never grep-and-guess). In chat, before writing code:
1. **Module map** — each tab: what the reader typed, what was computed, what was shown.
2. **Constants** — every table/score/threshold/list/text → goes to rule JSON verbatim.
3. **Doctrine diffs** vs classical / our engine → each becomes a knob, THEIR value default.
4. **Bugs** — name them; keep intent, not the bug. Keep THEIR quirks that are doctrine (AstroGaami
   caps the avoid list at 3 so "Postpone:" never shows — kept, knob `hora_bad_max`).

## 3. Zero typed input

Every fact the reader typed comes from the ecosystem (table in `institute-onboarding` §2 — chart
= My Charts subject via `useKpSubject` + `KpSubjectPicker`; stars/lords/panchang/sunrise/hora/dasha
= ops). What the reader CHOOSES stays a control (date, place via `LocationSearch`, stars to compare
via checkboxes/`SearchSelect`, a search word). Buttons never greyed on first open; an empty click
says what to pick.

## 4. Ops — reuse, then extend generically

1. Inventory first (`op_catalog.py`; Explore agent). Most astrology exists: `planet_nakshatra`,
   `nth_lord_from`, `lord_of_houses`, `navatara_chakra`, `tara_bala`, `panchanga`, `hora`,
   `kota_chakra`, `rows_where`, `rows_view`, `lookup`, `decision_table`, `pick_top`, …
2. Missing → ONE generic op whose every judgement is a param. Litmus: could another school with
   a different doctrine use it by changing JSON only? (`tara_matrix`: sources × targets; scores /
   favourable / names / bands / tiers / groups / pair_labels are params; count = the ONE existing
   `nakshatra_disha._score`.) A missing variant of an existing op = a new param (`hora mode`).
3. Declare in `op_catalog.py` with a comment naming every param and field; chart-free ops dispatch
   above the D1 guard in `eval_value`; nested `{vop}` args resolve through `eval_value`.
4. A new judgement the platform owns (access, navigation, commerce) = a chip on a generic op
   (`decision_table`, `literal`, `rows_view`) with `test_cases`, never Python.

## 5. Rule JSON

- Id `<prefix>_<module>` (institute code, e.g. `ag_`; ours use `fyi_<source>_…`). Control rule:
  `expr {note: calculation control}`, `metadata.control/calculation_control: true`.
- `metadata.workspace` + `surfaces: [<slug>]` for institute modules (hides from shared catalogs,
  404 to non-members).
- `metadata.provenance`: closed-set `kind` (`site` for a tool) + `work` + `author` + `locator`.
- All constants + the exprs the screen sends under one key (`metadata.<code>`), edited by the
  recursive JsonTreeEditor — so the owner can re-point a source without a rebuild.
- Write with a DISPOSABLE builder in the scratchpad (heredocs >5 KB truncate — use the Write tool).
  Then `python backend/rules_sync_check.py --to-db <id>` (local).
- FYIs (per-technique scorecards) instead of a control → `fyi-builder-agent`. Books → `book-to-assets`.

## 6. The control

- Loads chart context (`POST /rule-engine/chart/context`) + the rule, then ONE
  `/rule-engine/rules/eval-values` batch for the first view; later views batch their own.
- Hooks at the top, above any early return (React #310). `common/Modal` for any popup.
- Place-bound astro times: format in the PLACE's zone + `zoneLabel(tz)`; server instants: `fmtWhen`.
- A reading screen wraps itself in `common/PageTools` (Save as PDF, magnify, Focus, Annotate) wherever it shows -
  its own page AND every popup that hosts it ("any where Progression Scan is there", owner 2026-10-11); the
  PageTools title also names the screen in a popup whose title words have not loaded. A hand-placed chart grid is drawn LARGE (Sky Date Finder floor 34rem: at 20rem four grahas in one
  sign spilled into the next box). Guard `readingToolbarAndChartSize.test.ts`.
- Every icon-or-text action button carries a `title` tooltip from the chip words (`date.progression_title`).
- Register in `Registry.ts` under the rule id. Reproduce EVERY tab of the source; match the
  AstroStage UI bar.

## 7. Access Control (every module, every tab)

- A module is an Access Control **screen**; each tab is a **function**.
  - Workspace module: `screens[]` row in `backend/data/workspaces/<slug>.json` with
    `functions: [{id: "<rule_id>.<tab>", label}]`. `authz.catalog()` merges it as surface
    `workspace`, id `<slug>.<key>` — no edit to `screen_catalog.json`.
  - Studio / Individual / GrahaUvacha module: a row in `backend/data/screen_catalog.json` whose
    `label` equals its menu title (`test_screen_labels.py`). Individual/GrahaUvacha menu titles
    live in chip `ui.section_titles` (`individual.<id>`, child `individual.<parent>.<id>`, site word
    `individual.<id>@grahauvacha`); moving a nav's names anywhere else means teaching
    `backend/scripts/screen_labels.py` the new source in the same change — a blind scraper made
    every portal label check pass vacuously (2026-09-30). Renamed a menu title (or wrote a catalog
    label by hand)? Run `python backend/scripts/screen_labels.py` in the same change - Sky Date Finder
    shipped catalog "Sky Date Finder — date a chart by the sky" vs menu "Sky Date Finder" (2026-10-09).
    A screen gaining functions later: `python -m scripts.backfill_function_grants <screen ids>` per DB.
- The control gates each tab with `useCanFunctionAnywhere('<rule_id>.<tab>')` (hooks at top), drops
  withheld tabs from the bar, and falls back to the first visible tab.
- The workspace shell wraps modules in `AccessProvider surface="workspace"`; `GET /workspaces/{slug}`
  returns only the screens `authz.can_screen` allows. The door (`access.workspace_door`) lets people
  in; their workspace groups decide modules and tabs, else the workspace's **Catch All · <Name>**
  (institute-onboarding §6a). Grant a new module to the Catch All if guests should use it.
- A route that spends money or exposes data also gets `require_screen` / `require_function`
  server-side — the UI gate is not the lock.

## 7a. Tenant wall (HARD) — a module never shows another institute's data

Owner's rule (2026-09-28): no institute sees another's data. Full table:
institute-onboarding §6d. For a module this means:

- **Anything it stores** (saved results, notes, uploads, feedback, logs) carries the owner's
  `user_id` AND the workspace (`slug` / `institute_id`) it was made in. Every list/read endpoint
  filters on both — never "all rows" behind a signed-in check.
- **Its rules** are tagged `metadata.workspace: <slug>`: readable only by whoever may enter that
  workspace (`rule_engine.inactive_for` → `access.workspace_door`), kept out of AstroStage's shared
  catalogs (`listed_hidden`). Never borrow another institute's `<code>_*` rule.
- **Any admin / report / count / analytics route** it adds → `Depends(admin_scope("<view>"))` +
  filter on `scope.ws` (members, `<slug>.*` screens, its own rows). Portal-wide data (Cloudflare,
  every institute, AstroStage access requests, users' assets, other sites' activity) → nothing inside
  a workspace; portal actions → `admin_scope.portal_only`. Never plain `require_portal_admin` —
  it ignores the workspace, so a Portal Admin inside it sees the whole portal.
- **Payloads about people** show only this institute's slice (roles, groups, home institute) —
  `portal_admin.scoped_user_payload`.
- **UI mirrors, server enforces:** hide portal-only panels when `getAdminWorkspace()` is set, but
  the route must refuse on its own.
- Guard: extend `backend/tests/test_workspace_admin.py::test_no_institute_sees_another*` — one person
  in TWO institutes, data in both, called from inside one: the other never appears; refusals are
  403 (asserted), not a later error.

## 8. How people reach it

- Workspace module: an item in the workspace's left menu (AstroStage.in sidebar; folders / order /
  names from Menu Builder `workspace.<slug>`, module search for 100s of modules) and a deep link
  `?screen=<key>` (`<slug>.astrostage.in/?screen=<key>`, or `?ws=<slug>&screen=<key>` locally).
- Every workspace already has **Charts ▸ Generate Chart, My Charts** as its top menu, always (chip `pin: "top"`) (chip
  `access.workspace_shared_screens`, institute-onboarding §6f) — the reader adds a chart there and
  the module's `KpSubjectPicker` lists it (one `jatakam_subjects` table for every AstroStage portal).
  Never build a chart form or chart list inside a module; never use the keys `generate-chart` /
  `my-charts` for a module (the workspace file's own key would replace the shared screen).
- Studio/portal module: its menu item (and `RouteTracker` if standalone).
- Every site has the **site switcher** in the PortalDock (`common/PortalSwitcher`): the six sites
  (chip `access.portal_sites`) + the workspaces this person may enter; the jump carries the session
  (`routers/auth_handoff.py`). A new site or workspace appears there by data, never by code.

## 8a. Agent + MCP scope check (owner, HARD, 2026-10-23 — every module, every new feature)

Every module/feature is checked for both, and the answer goes in the end-of-turn report line
**Agent / MCP** (CLAUDE.md). Propose, never build on your own: the owner says yes first.

**Agent candidate = ANY of:**
1. A person repeats the same 3+ click sequence on this screen.
2. It should run on a schedule or trigger (daily, a new chart, a transit hit, a new row).
3. It works on many records at once (a cohort, all users, all chapters).
4. It needs draft → owner approves → write.

Yes → a recipe chip `agents.recipe.<id>` on the ONE runtime (`services/agent_runtime.py`); a missing
step = ONE generic action in chip `agents.actions` + `services/agent_actions.py`. Never per-agent code.
AI steps are priced and run under PaidRun; most steps are ops and free.

**MCP tool candidate = ALL of:**
1. The module has a read-only op: fact in → fact out (chart → dasha, date → panchang, rule → verdict).
2. The answer makes sense outside the portal (another AI could use it).
3. It shows no other person's data (tenant wall §7a + deny-wins Access Control).

Yes → a row in chip `mcp.tools` (tool → op/chip/recipe, input schema, Access Control function) on the
ONE generic MCP door. Until that door exists, list it as a candidate in the report. Once it exists, a
read-only tool row may be added in the same change (free, gated); a write tool always waits for the owner.

**No** → say why in one phrase ("no repeat, no schedule", "writes only", "shows other users' data").

## 9. Tracking, How-to, tour

- Portal Activity: workspace modules report `trackScreen({surface: 'workspace', view: '<slug>.<key>'})`
  from the shell — nothing per module. A new standalone route → `RouteTracker`.
- **A screen that polls (asks the server by itself on a timer) → list that request in chip
  `activity.background_checks`** (`METHOD /path`, `*` = one path part, a plain name). The audit list
  folds those into one row per sitting with a count; a poll left out drowns the screens people really
  opened (2026-10-28: Raju had 9 page visits and 9,985 audit rows, almost all `GET /connect/ring`).
  Never list a request that changes something (a POST that sends/saves). Guard
  `backend/tests/test_activity_background_checks.py`.
- How-to key + its **Guide Me script** (skill `guide-me-script`, 2026-09-28 — replaces the MP4 tour):
  `backend/data/guides/workspace-<slug>/<key>.json`, portal `workspace:<slug>`, one per module screen,
  `data-tour` hooks added to the control in the same change. Not sure which portal/workspace the module
  belongs to? ASK before writing it.
- **Tour Video (HARD, same change — skill `module-tour-video`):** the Guide me script alone is not done.
  Add the page's row in `tools/tour_video/video_settings.json` (`start_url` the demo account opens,
  `before`/`setup` `pick_chart` a demo chart), run `make_tour.py <key> --check`, read every shot, render.
  Op `guide_drift` (`video_missing` / `guide_stale` / `video_stale`) must stay 0.
